# Performance

Everyday workloads at 100,000 and 1,000,000 rows, each driver in its own
process against the same MySQL 8.4 on the same machine, over plain TCP. The
more rows an application reads or writes, the bigger the difference. When the
time goes into the network round trip of many tiny queries, or into building
ORM objects one by one, every driver gets closer to the others.

mysql-connector-python runs with its C extension, on Python 3.14 (it has none
for 3.15 yet). The asyncio sections compare `rustmy.aio` with asyncmy,
aiomysql and `mysql.connector.aio`.

## Why it is fast

- **Batches with the GIL released.** Rows are read in batches of about
  4 KiB with the GIL released, and each batch is converted in Rust while the
  server sends the next one: network and conversion overlap.
- **No intermediate objects.** Values go straight from the wire to Python
  objects; `date`, `datetime` and `timedelta` are built directly, and dict
  rows are built in Rust with their keys created once per result.
- **Out of the garbage collector.** Tuple rows of atomic values (numbers,
  text, bytes, dates, `None`, `Decimal`) are untracked as they are built, so
  collections during a large read do not traverse every row read so far.
- **Fewer round trips.** `executemany` batches `INSERT … VALUES` into
  multi-row statements and pipelines everything else.
